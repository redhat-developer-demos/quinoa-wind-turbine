# Plan for 4.1: secretly boost a team

This implements a focused version of [roadmap feature 4.1](../roadmap.md#41-add-power-ups-and-sabotage)
in one PR. The goal is a demo scenario, not a gameplay feature: quietly rig a race so one team pulls
ahead, then uncover why in Confluent Cloud afterwards. A new `race-modifiers` topic carries the boost
events, the Kafka Streams topology joins them with power before aggregating, and the only way to
trigger one is a deliberate, hidden call — the authenticated admin MCP tool, or a fallback URL.

The boost is invisible in the app on purpose. Nothing about it shows on the dashboard or the phones,
so the audience only sees one team mysteriously winning. The explanation lives in the `race-modifiers`
topic, which the Confluent segment inspects: consumer lag, the lineage from `power` and
`race-modifiers` into `race-progress`, and a Flink SQL query over the modifier events. The trigger
being an authenticated MCP call ties it to the Quarkus/LangChain4j MCP auth and Keycloak sessions, and
lets an agent such as Bob do the rigging with a valid admin token.

The roadmap's broader ideas — random power-ups for players, phone notifications, a dashboard badge, a
random scheduler — are dropped. They add gameplay but demonstrate none of the session themes
(Confluent, MCP auth, Keycloak, the code assistant), and surfacing a modifier would give away the
thing the investigation is meant to reveal.

## The modifier event

Add a `RaceModifier` record, serialized with `ObjectMapperSerde` and annotated
`@RegisterForReflection` like the other Kafka records:

```java
record RaceModifier(int team, double multiplier, long durationMs, String raceId) {}
```

A `multiplier` above 1 boosts a team, below 1 sabotages it, so one record covers both. `durationMs`
sets how long it applies; a large value rigs the rest of the race, a short one is a brief gust. Every
modifier is sent with `RaceTopology.raceMessage(...)`, so it lands on the `race` key and partition 0
and the single Streams task sees it in order with power and game events.

## Join modifiers in the topology

In `RaceTopology`, add `RACE_MODIFIERS_TOPIC = "race-modifiers"`, a third source stream, and a
`RaceInput.ModifierReceived(RaceModifier)` case merged into the existing stream:

```java
KStream<String, RaceInput> modifiers = builder
    .stream(RACE_MODIFIERS_TOPIC, Consumed.with(Serdes.String(), new ObjectMapperSerde<>(RaceModifier.class)))
    .mapValues(RaceInput.ModifierReceived::new);
KStream<String, RaceUpdate> updates = power.merge(gameEvents).merge(modifiers).process(...);
```

Keep active modifiers in the `Race` state record, one per team, as `ActiveModifier(double multiplier,
long expiresAtElapsedMs)`. When a modifier event arrives during a running race, `RaceProcessor` records
it for the team with `expiresAtElapsedMs = raceElapsed + durationMs`. In `onPower`, before adding the
quantity to the team total, multiply it by the team's active modifier when `raceElapsed <
expiresAtElapsedMs`, and round to a whole number. Apply it to the team total only, not to the player's
`generated`, so the leaderboard stays individual effort. A modifier that has expired by the next power
event no longer applies, which covers expiry mid-race; power already counted keeps its value.

The active modifier stays in the server-side `Race` store and is deliberately not added to the
`RaceState` snapshot, so it never reaches the dashboard, the phones or the read-only MCP tools. The
only observable effect is the team's power and distance moving faster or slower. A reset clears it with
the rest of the race state.

## Trigger a boost

Both triggers produce to `race-modifiers` through one `@Channel("modifiers-out")
Emitter<RaceModifier>` and `GameResource.sendModifier(team, multiplier, durationMs)`, which wraps the
record with `raceMessage(...)` like `sendGameEvent` does.

- Admin MCP tool. Add an admin-only `boost_team` tool in `RaceTools` next to `start_race`, on
  `@McpServer(ADMIN_SERVER)` only, taking `team` and optional `multiplier` and `duration` arguments
  (defaulting from config). It needs a bearer token with the `admin` role, so it's the authenticated,
  hidden path an agent uses. This is the primary trigger.
- Fallback URL. Add `GET /api/cheat?team=N`, with optional `multiplier`, `kind` and `duration` query
  params, that calls the same method. It's anonymous and unlinked, for quickly rigging a race from a
  phone browser without a code assistant. It isn't in the dashboard, so the audience doesn't see it.
  Guard it so it can't be stumbled on or left on by accident: a configurable secret key
  (`game.cheat.key`, required as `&key=` when set) and an on/off switch (`game.cheat.enabled`). The
  path must be excluded from the admin permission so it stays anonymous.

## Configuration

Add a `Modifiers` interface to `GameConfig` under `game.modifiers.*`, following the `Commentary`
pattern:

- `boostMultiplier` (default `2.0`) and `sabotageMultiplier` (default `0.5`) — the defaults the
  triggers use when a call doesn't specify one.
- `duration` (`Duration`, default e.g. `10s`) — the default effect length; a trigger can override it,
  and a long value rigs the whole race.

Add `game.cheat.enabled` (default `true`) and `game.cheat.key` (default empty) for the fallback URL.
Pass the multiplier bounds the topology needs into `RaceTopology.build(...)` as a small record, the way
`rules()` is passed today, or keep all modifier maths in the producer so the topology just applies
whatever multiplier the event carries. Prefer the latter: the event carries the final multiplier, so
the topology stays a pure join and the config lives with the triggers.

## Topics in every environment

Add `race-modifiers` wherever the other four topics are declared:

- `application.properties`: the Dev Services partition count, the outgoing channel binding, and the
  `quarkus.kafka-streams.topics` list.
- `src/main/kubernetes/openshift.cluster.yml`: a `KafkaTopic` with one partition, three replicas and a
  short `retention.ms`, since modifiers are transient.
- `scripts/confluent-provision.sh` and the Confluent section of `docs/openshift-install.md`: the topic
  create command, and add `race-modifiers` to the four topics the service account is granted.
- The software-template Helm `kafka-topics.yaml` in `WindTurbineInc/software-templates`, per the
  per-topic convention.

## Tests

- `RaceTopologyTest` with `TopologyTestDriver`: a boost raises a team's distance for the same power, a
  sabotage lowers it, a modifier stops applying after it expires mid-race, and a modifier for one team
  doesn't affect another. Assert the modifier never appears in the published `RaceState` snapshot.
- `RaceToolsTest`: `boost_team` rejects an anonymous caller and accepts an admin token, and produces a
  modifier.
- The `/api/cheat` endpoint: it produces a modifier for the given team, honours the key when one is
  set, and returns 404 or 403 when disabled.

## Demo moment

Mid-race, call `boost_team` through the admin MCP server (or hit `/api/cheat?team=1` from a phone).
One team pulls ahead with no on-screen explanation. Afterwards, open Confluent Cloud and find the
`race-modifiers` events, the lineage into `race-progress`, and a Flink SQL query that shows exactly
when and by how much the race was rigged — the authenticated MCP call that nobody saw.
