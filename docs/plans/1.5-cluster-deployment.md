# Plan for 1.5: deploy the game with Strimzi or Confluent Cloud

This implements [roadmap feature 1.5](../roadmap.md#15-deploy-the-game-with-strimzi-or-confluent-cloud).
It makes the cluster deployment repeatable on OpenShift against two Kafka providers, consolidates
the OpenShift configuration that the profiles duplicate today, and runs the cluster checks that
features 1.3 and 1.4 deferred. The Strimzi path is built and verified first; Confluent Cloud follows
once Strimzi passes its checks.

Status: planned. Unlike 1.3 and 1.4, this feature has a cluster to deploy against. The target is an
OpenShift sandbox (`api.ocp.485fj.sandbox1374.opentlc.com`), logged in as a cluster-admin. Each
section below is a separate PR; the order follows the dependencies, since both Kafka paths need the
shared application, Infinispan and secret setup first.

## What the target cluster already provides

The plan is grounded in what the sandbox serves today, checked with `oc` before writing it:

- The Keycloak operator is installed and its CRDs serve `k8s.keycloak.org/v2alpha1` only. The current
  `src/main/kubernetes/keycloak/keycloak.yaml` uses `v2beta1`, so it fails to apply unchanged. This
  confirms the version mismatch the roadmap flagged.
- No Kafka operator and no Infinispan operator are installed yet. OperatorHub offers Red Hat
  `amq-streams` (the Red Hat Streams distribution) and community `strimzi-kafka-operator` for Kafka,
  and Red Hat `datagrid` and community `infinispan` for Infinispan.
- `src/main/kubernetes/openshift.cluster.yml` has the Route and the four `KafkaTopic` resources, but
  no `Kafka`, no `KafkaNodePool` and no Infinispan. `docs/openshift-install.md` tells the operator to
  create the Kafka cluster `my-cluster` by hand and to install Infinispan from its Helm chart.

The install doc also still lists AMQ Streams Kafka 3.x with a manually created cluster, and creates
Infinispan with the Web Console Helm chart rather than a checked-in resource. Both become repeatable
manifests in this feature.

## Scope and provider order

Build and verify Strimzi first, then Confluent Cloud. The shared work comes before either, because
the consolidated application deployment, Infinispan, Keycloak and the secrets are prerequisites for
running the game at all. Keep Confluent optional: the default build carries no Confluent libraries,
messages stay JSON through Jackson, and selecting Confluent Cloud only changes configuration and the
provisioned resources.

## PR 1: consolidate OpenShift config and select the profile per provider

The three deployment profiles in `application.properties` (`openshift-cluster`, `openshift-sandbox`,
`confluent`) repeat the same Infinispan client settings, route TLS and deployment target. Pull the
shared settings into one place so a provider profile only sets what differs from it, and keep all
three profiles usable. The `prod` profile currently hard-codes
`quarkus.kubernetes.env-vars.QUARKUS_PROFILE.value=openshift-cluster`, which forces every deployment
onto the Strimzi profile. Replace that so a Confluent deployment runs with `QUARKUS_PROFILE=confluent`
instead, selected at deploy time rather than baked into the image.

Verify that switching providers needs only deployment configuration, by deploying the same image once
with each profile without rebuilding and without changing serializers. The payloads stay JSON in both
cases.

## PR 2: deploy Infinispan as a checked-in resource

Replace the manual "create it from the Web Console Helm chart" step with a repeatable Infinispan
deployment that has persistent storage and explicit counter and cache configuration for the game's
state. Its service name and authentication secret must match the app configuration directly, instead
of relying on the operator-generated `infinispan-generated-secret`. The profiles today map
`infinispan-password` from that generated secret; point them at a secret this feature owns, and allow
an existing Infinispan service to be supplied by overriding `infinispan-host`, `infinispan-username`
and the password secret.

Separate deployments must keep independent game state, including their Infinispan counters, so two
namespaces (for example one Strimzi and one Confluent) can run side by side without sharing the race
ID or user counters. Confirm this by running both and checking that a reset in one does not change
the other's counters.

## PR 3: own the shared secrets in the deployment

Create secret references the deployment keeps across a redeploy, rather than variables set with
`oc set env` that the Quarkus OpenShift extension drops when it replaces the deployment:

- the dashboard password as `GAME_ADMIN_PASSWORD` from the `game-admin` secret,
- the Infinispan credentials from the secret in PR 2,
- one shared `quarkus.http.auth.session.encryption-key` for every replica.

The session key is the [open follow-up](../roadmap.md#open-follow-ups) that breaks dashboard login
across pods: without a shared key each pod encrypts the login cookie with its own, so with five
replicas a session only works on the pod that created it. The same fix covers `/ws/dashboard`. Supply
team configuration, the AI flag and the model settings through deployment configuration, with the
OpenAI API key as an optional secret. Template commentary must still work when that secret is absent.

## PR 4: fix the Keycloak manifest and split realm import from instance creation

Admin MCP stays optional, as it is today: without Keycloak the app starts and `/admin/mcp` rejects
every call. The realm import `wind-turbine` carries the admin role, the audience mapper, the MCP
client and the OAuth callbacks. Configure the external issuer URL and the certificate trust the app
pods need when they call Keycloak through the router's external host, which is the deferred 1.3
cluster check.

Split `src/main/kubernetes/keycloak/keycloak.yaml` into two parts so a realm import never replaces an
existing installation:

- a realm-import-only manifest with the `wind-turbine` `KeycloakRealmImport` and its password secret,
  applied into the namespace the operator watches,
- a full-instance manifest with the PVC, PostgreSQL, the `Keycloak` CR and the realm import, for
  clusters that have no Keycloak yet.

Both target the `k8s.keycloak.org/v2alpha1` API the operator serves, instead of the `v2beta1` the
current file uses, with the field names checked against that version.

On the target cluster, reuse the existing RHBK-managed instance `keycloak/keycloak` that already
serves the `sso` realm at `sso.apps.ocp.485fj.sandbox1374.opentlc.com`. The operator is
single-namespace (`OwnNamespace`/`SingleNamespace` only, `MultiNamespace` and `AllNamespaces`
unsupported) and watches only the `keycloak` namespace, so the realm import goes there alongside
`sso`, and the game's password secret goes into the same namespace. A realm import is per-realm, so it
adds `wind-turbine` without touching `sso`. The app in the demo namespace points at
`GAME_OIDC_URL=https://sso.apps.ocp.485fj.sandbox1374.opentlc.com/realms/wind-turbine`. The
full-instance manifest stays documented for clusters where no Keycloak exists or the operator watches
the deployment namespace.

## PR 5: deploy Strimzi Kafka with KRaft and the topics

Replace the manual Kafka 3.x/ZooKeeper cluster with a KRaft deployment supported by the chosen
operator release. Add `Kafka` and `KafkaNodePool` resources with three brokers and a controller
quorum, persistent volumes and the topic operator, to `src/main/kubernetes/openshift.cluster.yml`.
Keep the four existing `KafkaTopic` resources, with the race inputs on one partition, `replicas: 3`,
`race-progress` compacted and `race-commentary` retained for one hour. Set replication to three for
the Kafka Streams internal topics as well, which the `confluent` profile already does and the Strimzi
profile must match. Supply the internal bootstrap endpoint
(`my-cluster-kafka-bootstrap:9092` today) and configure listener authentication, TLS and the matching
secrets consistently for both reactive messaging and Kafka Streams.

Document the operator install and its namespace scope, including the Red Hat Streams distribution
(`amq-streams`) where that is the right choice for OpenShift.

## PR 6: parameterize and harden the application deployment

Create one application deployment definition with the knobs a real deployment needs: namespace, image
registry and tag, route host, replica count, resource requests and limits, storage class and the
dependency endpoints. Build with Java 25 and a unique image tag per build. Configure startup,
readiness and liveness probes, an HTTPS route and graceful shutdown for the WebSocket connections, so
a rolling update does not drop players mid-race. Deploy directly first; keep GitOps and Pipelines
(`docs/gitops-pipeline.md`) as documented optional automation, not a prerequisite for running the
game.

## PR 7: add the provider choice to the software templates

Both software-template variants and their Helm charts gain the provider choice. Include Strimzi
resources only for the Strimzi option and Confluent connection secrets only for Confluent, while the
shared Infinispan, Keycloak, application and route configuration stay in both paths. The template's
Kafka manifest moves to the same KRaft deployment as PR 5. Each chart's `templates/kafka-topics.yaml`
already lists the four topics from 1.1 through 1.4; keep them aligned with the manifest here.

## PR 8: Confluent Cloud path

Keep Strimzi operators and Kafka custom resources out of this path. Provide repeatable Cloud topic
and permission provisioning with the same four topic names, partition counts and retention as Strimzi,
and allow an existing Cloud cluster. Wire `CONFLUENT_BOOTSTRAP_SERVERS`, `CONFLUENT_API_KEY` and
`CONFLUENT_API_SECRET` through deployment configuration and secrets, and apply the SASL/TLS settings
to both reactive messaging and Kafka Streams, which the `confluent` profile already sets. Keep
internal-topic replication at three. Grant access to the application topics, the shared commentary
consumer group, the per-replica consumer groups and the Kafka Streams internal topics and groups,
accounting for the current UUID-based group names (`group.id=${quarkus.uuid}`). Topic and ACL
provisioning must finish before the app rolls out, since Confluent Cloud does not create topics on
first use.

## PR 9: documentation

Rewrite `README.md` and `docs/openshift-install.md` with the full prerequisites, build and deploy
steps, secret setup, dependency readiness checks and cleanup for each provider. Say which resources
each path creates and which existing services can be reused, keep credentials out of source control,
and distinguish deleting the app from deleting persistent data or Cloud resources.

## Cluster verification

Run the same acceptance checks against both providers, AI disabled first and then with OpenAI once
credentials are available. These roll in the deferred 1.3 and 1.4 cluster checks.

- Rollout and dependency health: the app, Infinispan, Kafka and (when enabled) Keycloak reach ready.
- Team configuration, dashboard login over HTTPS, player WebSockets, read-only MCP at `/mcp`, and
  authenticated admin MCP at `/admin/mcp` with a Keycloak token.
- A `GameLoader --ws` race to the finish with a few browser contexts for the UI, checking race
  progress and finish, commentary timing and team names, pause/resume, reset and reconnect replay.
- Scale to five replicas and confirm login works across pods (the session-key fix in PR 3), every
  dashboard receives the same commentary IDs, and only one consumer owns commentary generation.
- Restart the Streams owner and the commentary owner during a race; check state recovery, partition
  reassignment and that stale commentary is not replayed.
- A new pod joining a running race, including the known game-status initialization follow-up where a
  pod that starts mid-race reports `empty` until the next game event.

Record failures and the fixes they need before marking either path verified.

Demo moment: deploy the same image once with Strimzi and once with Confluent Cloud, then run the same
race checks through each deployment's route.
