# Plan for 1.3: expose race control as an MCP server

This is the implementation plan for roadmap feature 1.3 in [`docs/roadmap.md`](../roadmap.md). It
lets agents such as Claude Code and goose read the race and, with the admin role, start, pause and
reset it. Since 1.1 every replica holds the current race in `RaceResource`, and game events go
through `GameResource.sendGameEvent`, so the MCP tools are thin wrappers around them. Most of the
work is security. MCP clients can't use the dashboard's form login, so the admin tools need OIDC
bearer tokens, with Keycloak Dev Services locally and the Red Hat build of Keycloak (RHBK) on the
cluster.

## Status

The implementation is committed on `main` as `1abf286`. The template chart change is commit
`6b6fad5` on the template's `wind-turbine-remote` branch. Cluster verification is deferred and
doesn't block feature 1.4, the race commentator. Browser OAuth login with Claude Code and goose
remains an unverified follow-up.

## What shaped the design

An MCP client starts its OAuth login only when the server answers with HTTP 401 and a
`WWW-Authenticate` header that links to the protected resource metadata. The Quarkiverse MCP server
answers a call to a tool secured with `@RolesAllowed` with an MCP error (-32005) instead of a 401,
so a single endpoint that mixes anonymous and admin tools would never get the client to log in. The
admin tools therefore get their own endpoint, guarded by an HTTP permission that returns the 401.

Quarkus OIDC serves the [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) protected
resource metadata when `quarkus.oidc.resource-metadata.enabled` is on. Claude Code accepts a
pre-registered OAuth client through `claude mcp add --client-id ... --callback-port ...`, so the
realm defines a public client with PKCE and Keycloak doesn't need dynamic client registration.

`quarkus-mcp-server-http` 2.0.3 is the latest release and is built against Quarkus 3.33, while this
project uses 3.40.1. The first implementation step checks that the two build and start together.

The RHBK operator may not be installed on every cluster the software template deploys to, so the
template creates the Keycloak resources only when a chart value turns them on. Without Keycloak, the
app runs with OIDC disabled: the read-only tools work and the admin endpoint rejects every call.

## Endpoints and tools

A new `RaceTools` class defines the tools on two MCP servers.

The default server at `/mcp` needs no login. It has `get_race_state`, `get_leaderboard` with an
optional team, and `get_player`, which returns one player's score, team and rank. It also exposes
the resource `race://current` with the race as JSON. Clients can subscribe to it, and the app sends
an update notification whenever `RaceResource.updates()` emits a snapshot.

The `admin` server at `/admin/mcp` needs a bearer token with the `admin` role. It has the same read
tools and resource, so an agent only needs one connection, plus `start_race`, `pause_race` and
`reset_race`. These call `GameResource.sendGameEvent`, which keeps game event handling in one place,
and that method's `@RolesAllowed("admin")` checks the caller a second time.

## Keycloak realm

Dev mode, tests and the cluster use the same realm layout:

| Item | Value |
|---|---|
| Realm | `wind-turbine` |
| Realm role | `admin` |
| App client | `wind-turbine`, confidential, used by the app to validate tokens |
| Agent client | `mcp-agent`, public, authorization code flow with PKCE (S256) |
| Agent redirect URIs | `http://localhost:33418/callback` and `http://127.0.0.1:33418/callback`, for Claude Code with `--callback-port 33418`, plus goose's callback once it's known |
| Audience | a mapper on `mcp-agent` adds `wind-turbine` to the access token audience |
| Admin user | `developer`, with the `admin` role |

The dev realm is `src/main/resources/keycloak/wind-turbine-realm.json`, imported by Keycloak Dev
Services. The `developer` password there is `developer`, a second user `player` has no admin role
for the tests, and `mcp-agent` allows direct password grants so tests and `curl` can get tokens
without a browser.

The cluster realm has no `player` user and no direct grants. Its `developer` password comes from
the `game-admin` secret through a realm import placeholder.

## Configuration

The admin MCP path gets an HTTP permission that uses the existing `admin-policy` and only the
bearer mechanism, so form login for the dashboard, `/ws/dashboard` and `/api/game/event` stays as
it is:

```properties
quarkus.mcp.server.admin.http.root-path=/admin/mcp
quarkus.http.auth.permission.mcp-admin.paths=/admin/mcp,/admin/mcp/*
quarkus.http.auth.permission.mcp-admin.policy=admin-policy
quarkus.http.auth.permission.mcp-admin.auth-mechanism=bearer
quarkus.oidc.application-type=service
quarkus.oidc.client-id=wind-turbine
quarkus.oidc.token.audience=wind-turbine
quarkus.oidc.resource-metadata.enabled=true
quarkus.keycloak.devservices.realm-path=keycloak/wind-turbine-realm.json
```

The implementation has to confirm that the 401 on `/admin/mcp` includes `resource_metadata`, and
that the metadata names `/admin/mcp` as the resource.

In production, OIDC is on only when the deployment sets it up:

| Variable | Meaning |
|---|---|
| `GAME_OIDC_ENABLED` | `true` turns OIDC on. It defaults to `false` outside dev and test. |
| `GAME_OIDC_URL` | The realm URL, for example `https://keycloak.apps.example.com/realms/wind-turbine` |
| `GAME_ADMIN_PASSWORD` | The dashboard password, read from the `game-admin` secret, key `password` |

Without these variables the app starts as it does today, and the sandbox and Confluent profiles keep
working.

New dependencies are `quarkus-mcp-server-http`, `quarkus-mcp-server-oidc` for insufficient-scope
responses and `quarkus-oidc`, plus `quarkus-mcp-server-test` and `quarkus-test-keycloak-server` for
tests.

## Cluster

In this repository, `src/main/kubernetes/keycloak/` holds a `Keycloak` and a `KeycloakRealmImport`.
They are applied by hand, because the resources in `openshift.cluster.yml` are always applied and
would fail on a cluster without the RHBK operator. `docs/openshift-install.md` describes the steps:
install the operator, create the `game-admin` secret, apply the Keycloak resources and set the
variables above. RHBK may require a database, so the implementation checks whether the operator
accepts a dev-file or ephemeral database for the demo and documents what it uses.

In the software template (`WindTurbineInc/software-templates`, branch `wind-turbine-remote`, PR
#19), the chart in `scaffolder-templates/quinoa-wind-turbine/manifests/helm/app` gets:

- `keycloak.enabled: false` in `values.yaml`
- a Vault `RandomSecret` and `VaultSecret` that create `game-admin` in every namespace, following
  the build chart's `vault-random-secret.yaml`
- the `Keycloak` and `KeycloakRealmImport`, only when `keycloak.enabled` is on
- `GAME_ADMIN_PASSWORD` from `game-admin` in `deployment.yaml` always, and `GAME_OIDC_ENABLED` and
  `GAME_OIDC_URL` when Keycloak is on

Keycloak's hostname has to be the external route host, because agents on laptops get their tokens
through it and the app checks the token issuer. The chart change needs to find where the template
knows the cluster domain. Because every namespace then has its own dashboard password, this also
closes the roadmap follow-up about per-deployment passwords.

## Tests

`RaceToolsTest` uses the MCP test client with real tokens from Keycloak Dev Services. It checks
that `/mcp` lists only the read tools and answers them without a login, and that `/admin/mcp`
answers an anonymous request with a 401 that includes `resource_metadata`. A `player` token gets a
403, and a `developer` token can start the race and then reset it to a new race ID. Another test
checks that `/.well-known/oauth-protected-resource` names the realm as the authorization server, and
a unit test covers the `get_player` ranking. `AdminLoginTest` keeps checking that form login works
next to OIDC.

## Verification

1. `./mvnw package` with all tests, and `./mvnw test -Pe2e`.
2. In dev mode, with the dashboard open in a browser: check the 401 and the metadata with `curl`,
   get a `developer` token and call `start_race` on `/admin/mcp`, watch the race start, and read
   `race://current` during a `GameLoader --ws` race.
3. The Claude Code login opens a browser, so the presenter runs it: approve the two game servers
   from the project's `.mcp.json`, authenticate `wind-turbine-admin`, then try a prompt such as
   "start the race and tell me when one team passes 50%". goose is checked the same way.
4. Deferred: cluster verification, including `helm template` with Keycloak on and off,
   `oc apply --dry-run=client` on the Keycloak resources, and a real deployment with the RHBK
   operator. Resume these checks when cluster testing is scheduled; they don't block 1.4.
