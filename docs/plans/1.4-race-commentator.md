# Plan for 1.4: add a race commentator

This implements [roadmap feature 1.4](../roadmap.md#14-add-a-race-commentator-with-or-without-an-llm)
in one PR. The dashboard displays short commentary when the race changes. Template lines work by
default, and `game.ai.enabled=true` lets a LangChain4j AI service write the lines instead. A slow
or failed model call falls back to the matching template.

Status: implemented in this PR. Cluster testing is deferred, as
agreed for 1.3. The sections below describe the implementation; completed checks are recorded
under [Verification results](#verification-results).

## Provider and configuration

Add only `io.quarkiverse.langchain4j:quarkus-langchain4j-openai`, using a release compatible with
the project's Quarkus version. OpenAI is the default service. A configurable base URL and model
name allow a local server to use the same client when it implements the required Chat Completions
API. No Ollama extension, dedicated profile or automatic model download is needed.

Use the [Chat Completions API](https://developers.openai.com/api/reference/resources/chat) for
short text requests. Keep requests to the common text generation fields, without tools, chat
memory or provider-specific features. Compatibility with each local server still needs a smoke
test when that server is introduced.

The [Quarkiverse configuration reference](https://docs.quarkiverse.io/quarkus-langchain4j/dev/includes/quarkus-all-config.html)
documents `quarkus.langchain4j.openai.base-url` and `quarkus.langchain4j.openai.chat-model.model-name`.
Expose these through `OPENAI_BASE_URL` and `OPENAI_MODEL`, with the base URL defaulting to
`https://api.openai.com/v1/`. Read the credential from `OPENAI_API_KEY`. Choose and document a
small hosted model during implementation, and leave its name overridable. A local server can use
a placeholder key if it doesn't require authentication but the client requires a nonempty value.

Set `game.ai.enabled=false` by default and connect the provider's `enable-integration` setting to
it. Quarkiverse documents this as a
[runtime setting](https://docs.quarkiverse.io/quarkus-langchain4j/dev/enable-disable-integrations.html).
Disable LangChain4j Dev Services explicitly. The coordinator selects the template directly when
AI is off, so it never invokes the AI service in that mode.

Before implementing the rest, verify with the selected extension release that the application
starts without a key when AI is off, and that the same packaged build can start with AI on or off
and different endpoint/model settings. Resolve any eager credential validation in this step.
Treat these as startup settings; this PR doesn't add a dashboard toggle or live config reload.

## Detect race events

Create a pure Java trigger detector that compares ordered `RaceState` snapshots. It tracks state
by race ID and emits structured triggers with the relevant facts. Templates and the AI service
receive the same trigger.

- Announce a lead change only when a team has a unique lead and differs from the previous unique
  leader. Ties and the initial all-zero state don't count as a lead change.
- Announce each team's 25%, 50% and 75% milestone once per race. If one snapshot crosses several
  milestones, announce the highest and mark the lower ones as crossed.
- Check player surges in non-overlapping five-second windows of running race time. A player
  qualifies when their generated-power increase is at least twice their preceding window and at
  least ten taps' worth of power. Require two complete windows and choose the largest qualifying
  increase per check. Make the window and thresholds configurable.
- Announce the winner once when a snapshot first becomes `FINISHED`.

Use ordered snapshots as the authority for lifecycle, finish and progress. The dashboard feed also
watches game events to hide commentary promptly on pause or reset. The generation coordinator
doesn't consume that independent stream, because replayed old events could cancel a newer snapshot's
pending line. Clear detector state on a
new race ID, ignore repeated or older snapshots, and establish a baseline when attaching to an
already running race so old milestones aren't announced again.

Coalesce routine triggers within a configurable interval, initially three seconds. Give finish
priority over lead changes, milestones and surges, and emit finish without waiting for that
interval. Keep at most one model request in flight and one pending trigger, replacing pending
routine triggers with higher-priority or newer ones. This bounds work when snapshots arrive
every 250 ms.

## Generate commentary across replicas

Every replica currently consumes all of `race-progress` to answer queries and feed its sockets.
Generating commentary from each local copy would multiply model calls by the replica count.

Add a separate commentary input channel on `race-progress`, using one stable consumer group
shared by all replicas. Race snapshots use partition 0, so one consumer owns generation. This
consumer feeds the trigger detector and coordinator, while the existing per-replica race input
stays as it is. Keep model calls off Kafka Streams and WebSocket event-loop threads.

Publish completed lines to a new `race-commentary` topic keyed by `race`, with a bounded retention
period. Each replica consumes the topic with its own group, caches the latest line for the
current race, and broadcasts it to its dashboard connections. A reconnect receives the latest
line if it belongs to the displayed race.

Each message has a deterministic event ID, race ID, trigger type, source snapshot timestamp,
creation timestamp, text and source (`template` or `ai`). Deduplicate deliveries by event ID,
discard lines from another race, and suppress late routine lines after pause or finish. Reset
clears the ticker and invalidates all pending model results. A result past its deadline never
replaces the fallback already emitted for that event.

Kafka delivery remains at-least-once. A consumer restart can repeat a model request before its
offset is committed, so this PR must not claim exactly-once model calls. Test reassignment and
baseline recovery locally to prevent a restart from replaying historical commentary.

Add the topic to Kafka Dev Services, the Strimzi resources and the Confluent CLI instructions in
`docs/openshift-install.md`. Include the matching software-template Helm topic change when
implementing the PR. Existing deployments work with AI off and need no new model secret.

## Templates and AI fallback

Define a `Commentator` interface with template and AI implementations. Keep templates deterministic
and based only on supplied facts, for example "Beach passes 50%." Team names, colors and cars
come from `game.teams.1.*` and `game.teams.2.*` in `application.properties`. The UI loads those
settings from `/api/config` before rendering. Templates and AI prompts use the same configured
names, so renaming a team changes its commentary too.

The LangChain4j `@RegisterAiService` receives a trigger and a compact summary of team distances,
positions and relevant player totals. Ask for one plain-text sentence using only those facts.
Treat player names as data. There is no tool access or conversation memory.

Start with a two-second end-to-end deadline and a 180-character output limit, both configurable.
Reject blank or overlong output and fall back on timeout, provider error or invalid output.
Disable automatic retries for this path so a slow endpoint doesn't build a backlog. Render text
through React's normal escaping. Keep request/response logging off by default.

## Dashboard and feature discovery

Extend `DashboardSocket.DashboardMessage` with `type: "commentary"` carrying the commentary record.
Use the existing per-connection stream cleanup. Add a ticker that remains visible for template
commentary, clears on reset and doesn't displace race controls or the winner display. Announce
new lines through a polite live region and respect reduced-motion preferences. Hold finish
commentary until the winning car completes its movement across the line, as with the winner panel.

Add anonymous `GET /api/features` returning `{"aiEnabled": false}` or `{"aiEnabled": true}` from
the runtime configuration. This reports whether AI is enabled, not whether the provider is
healthy. Each commentary message identifies whether its line came from AI or a template.

## Implementation and verification

1. Add the extension and configuration, verify disabled startup without credentials, and verify
   that a packaged build can change endpoint, model and AI flag on restart.
2. Implement the detector, templates and bounded coordinator with unit tests for ties, skipped
   milestones, surge windows, repeated snapshots, pause, reset and finish priority.
3. Add the shared generation consumer, commentary topic and per-replica delivery. Test with two
   local consumers that only one generates, while both dashboard replicas receive the result.
4. Add the AI service and test against a local fake OpenAI-compatible HTTP endpoint. Cover a
   valid line, timeout, HTTP error, blank/overlong output and a late response after reset. Verify
   zero model requests with AI disabled. Automated tests need no paid API access.
5. Add feature discovery and the dashboard ticker. Extend socket tests for commentary delivery
   and reconnect, then check the ticker and reset in a browser with a few players.
6. Update the README with startup configuration and a custom-endpoint example. Run the default
   Maven tests and frontend build, then a `GameLoader --ws` race with templates. When credentials
   are available, repeat with OpenAI and deliberately break the endpoint to check fallback.

Use `GameLoader` for simulated players and keep browser verification at low concurrency.
Cluster deployment tests and a local-model smoke test are deferred. Record completed checks and
remaining checks in this plan when the implementation is ready.

## Verification results

The default Maven suite passes 74 tests with no failures, errors or skips, and `./mvnw package`
completes successfully. Tests cover detector rules, coalescing,
timeouts, lifecycle invalidation and late results, plus a local OpenAI-compatible HTTP server.
The HTTP checks verify authentication, model selection, compact prompts, invalid output and
provider failure fallback, and no requests when AI is disabled. The AI service has no chat memory.

`CommentaryDeliveryTest` runs a real Kafka race with two dashboard sockets and checks identical
lead/milestone messages, reconnect replay, duplicate suppression, reset and stale-race rejection.
`CommentaryFeedTest` covers startup replay ordering and pause/resume boundaries. Topology tests
cover delayed finish records and publication timestamps restored from the state store.

Seven frontend tests cover commentary ordering and loading team configuration from the server.
The AI integration tests override the team names to Alpine and Coast and verify that `/api/config`,
template fallback and AI prompt facts all use those configured values.

Dashboard stream tests cover both close-before-subscription and close-after-subscription cleanup.

The same packaged artifact was started with AI disabled, then with AI enabled and a custom
endpoint/model backed by a local fake HTTP server. Both starts served the expected `/api/features`
value and race state. This verifies that those settings can change on restart without rebuilding.

A browser check played a two-player race through lead and 25% milestone commentary, pause/resume,
and finish. Screenshots at a 1400 × 806 viewport confirmed the ticker stays readable above the
track without overlapping the controls or winner panel. Reloading the finished race restored its
commentary. Reset cleared both the ticker and winner panel and returned the dashboard to the
waiting state. A four-player `GameLoader --ws` run completed with both teams at 100%, a winner
after 15.3 seconds, health `UP` and no HTTP server errors in Prometheus metrics.

`./mvnw test -Pe2e` passes with one Chromium process and four isolated player contexts. It captures
the winning car's computed position when win commentary first appears and requires it to have
completed the track. It also checks the configured winner name, cached commentary after reload
and clearing the ticker and winner panel on reset. Finish and reset screenshots were inspected.

The selected Quarkiverse release is 1.14.1, used with Quarkus 3.40.1. Its `max-retries` property
rejects zero, but the underlying LangChain4j 1.20 client interprets one as an additional retry.
`CommentaryModelCustomizer` sets the underlying builder to zero retries, and the HTTP test
checks that a 503 produces only one request. `AiCommentator` activates a CDI request context for
the request-scoped AI service when called on the background thread.

Hosted OpenAI and a real local model haven't been called because no OpenAI API key or local
model server was available in this session. Cluster checks remain deferred.
Ownership revocation and reassignment baselines are covered by unit tests; multiple application
replicas and broker-driven ownership failover remain part of that deferred verification.

Keycloak/OIDC and OpenAI are disabled by default in every mode. `OptionalServicesDisabledTest`
points both providers at unavailable URLs and verifies a complete race with template finish
commentary, dashboard form authentication, public read-only MCP and denial of all admin MCP
requests. The separate OIDC-enabled profile verifies bearer authentication and rejects dashboard
cookies as a substitute for tokens. Browser E2E asserts that both optional services are disabled
before running its four-player race.
